# 아키텍처

**Unified Harness Protocol, 버전 `2026-08-11`**

이 명세에서 MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, MAY,
OPTIONAL 이라는 핵심어는 모두 대문자로 나타날 때, 오직 그때만 [RFC 2119][rfc2119] 와
[RFC 8174][rfc8174] 에 기술된 대로 해석돼야 한다.

[rfc2119]: https://www.rfc-editor.org/rfc/rfc2119
[rfc8174]: https://www.rfc-editor.org/rfc/rfc8174

## 1. 역할

```
┌──────────┐   UHP over HTTP   ┌──────────┐   implementation-defined   ┌──────────┐
│  Client  │ ────────────────▶ │  Server  │ ─────────────────────────▶ │ Harness  │
└──────────┘                   └──────────┘                            └──────────┘
```

**클라이언트** — 작업이 수행되기를 원하는 애플리케이션이다. 제품 백엔드, CLI, CI 잡, 또 다른
에이전트일 수 있다. 클라이언트는 오직 UHP 만 말한다. 서버 뒤에서 어느 하네스 구현이 실행되는지도,
서버가 그것을 어떻게 실행하는지도 알아야 할 필요가 없다(MUST NOT).

**서버** — 이 명세를 구현한다. 태스크를 받아들이고 하나 이상의 하네스를 구동하며, 여기서 정의된
어휘로 진행 상황과 결과를 보고한다. 하네스를 *어떻게* 실행하는지에 대한 모든 것 — 컨테이너,
서브프로세스, 큐, 원격 워커 — 은 이 명세의 범위 밖이며 와이어 포맷으로 새어 나가서는 안 된다
(MUST NOT).

**하네스** — 자신의 루프와 도구와 세션 상태를 가진 완전한 에이전트 런타임이다. UHP 는 하네스
자체를 명시하지 않는다. 클라이언트가 서버를 통해 하나를 어떻게 구동하는지를 명시한다. 하네스는
**base** 로 식별된다. `codex`, `claude-code`, `hermes` 와 같은 안정적인 문자열이다.

**구성된 하네스** 는 base 에 설정을 더한 것이다 — 기본 모델, 시스템 프롬프트, 도구 제한, 스킬,
MCP 서버, 스텝과 시간 예산. 이것은 클라이언트가 작업을 보낼 때 선택하는 단위이며, 서버가 부여한
id 로 주소가 매겨진다.

> 왜 base 만이 아니라 구성된 하네스인가?
> 같은 base 라도 다른 시스템 프롬프트, 다른 모델, 다른 도구 집합에서는 아주 다르게 행동한다.
> 설정을 일급의, 주소 가능한 객체로 만든다는 것은 제품이 백엔드를 재배포하지 않고도 에이전트의
> 행동을 바꿀 수 있다는 뜻이고, 두 제품이 행동을 공유하지 않으면서도 하나의 서버를 공유할 수
> 있다는 뜻이다.

## 2. 적합성 클래스

서버는 자신이 구현하는 클래스를 선언한다. 각 클래스는 누적된다. Extended 는 Core 를
포함하고, Full 은 Extended 를 포함한다.

| 클래스 | 이 클래스의 서버가 반드시 구현해야 하는 것 |
|---|---|
| Core | 캐퍼빌리티 디스커버리, 하네스 디스커버리, 스트리밍/비스트리밍 태스크 실행, 세션 이어가기, 취소, 오류 모델. |
| Extended | Core 에 더해 파일 입력, 아티팩트 조회, 세션 목록/조회. |
| Full | Extended 에 더해 하네스 라이프사이클 관리(생성, 수정, 삭제)와 세션 공유. |

클라이언트는 캐퍼빌리티 디스커버리를 확인하지 않고서는 Core 이상의 어떤 능력도 가정해서는 안
된다(MUST NOT)([Lifecycle §2](https://github.com/HarnessRouter/harnessrouter/blob/main/protocol/versions/2026-08-11/lifecycle.md) 참고). 서버는 구현하지 않은 능력을
광고해서는 안 된다(MUST NOT) — 광고는 약속이며, 그것을 신뢰했다가 `404` 를 받은 클라이언트는
되돌릴 수 없는 방식으로 속은 것이다.

[적합성 스위트](https://github.com/HarnessRouter/harnessrouter/tree/main/protocol/versions/2026-08-11/../../conformance/) 는 각 클래스를 별도로 테스트하고 클래스별로
보고한다. 어떤 클래스에서 통과한 서버는 자신을 "UHP 2026-08-11 conformant (<class>)" 로 설명해도
된다(MAY). "conformant" 라는 용어의 다른 용법은 의미가 없다.

## 3. 객체 모델

여섯 가지 객체 타입이 있다. 모든 객체는 자신의 타입을 이름 짓는 `object` 필드와, 식별자가 무엇을
가리키는지 결코 모호하지 않도록 타입을 구분하는 접두사가 붙은 `id` 를 가진다.

| 객체 | `object` 값 | Id 접두사 | 수명 |
|---|---|---|---|
| Harness | `harness` | `chrn_` | 삭제될 때까지 |
| Response | `response` | `resp_` | 서버 정책에 따라 보존 |
| Session | `session` | `hsess` | 삭제될 때까지 |
| File | `file` | `file_` | 자신의 컨테이너와 함께 |
| Container | `container` | `cntr_` | 자신의 세션과 함께 |
| Event | *(없음 — 이벤트는 `type` 을 가진다)* | — | 스트리밍되며, 재생 가능 |

이들의 관계:

```
Harness ──┐
          ├──▶ Session ──┬──▶ Response ──▶ Response ──▶ …    (태스크당 하나, 체인)
Model  ───┘              └──▶ Container ──▶ File, File, …    (아티팩트)
```

- response 는 하나의 태스크다. 하나의 요청이 들어가고 하나의 결과가 나온다. 이것이 작업의
  원자 단위다.
- session 은 대화 맥락과 작업 디렉터리를 공유하는 response 들의 체인이다. session 은 첫
  태스크에 의해 암묵적으로 만들어지고 `previous_response_id` 로 확장된다.
- container 는 session 의 파일 네임스페이스다. 에이전트가 쓰는 파일이 그 안의 아티팩트가
  된다.

> 왜 세션이 암묵적인가?
> 어떤 작업이든 하기 전에 `POST /sessions` 를 요구하는 것은 왕복 하나와 실패 모드 하나와
> 정리해야 할 객체 하나를 추가하는 셈이 된다 — 대부분의 첫 태스크가 전혀 필요로 하지 않는
> 개념을 위해서 말이다. 일회성 태스크만 보내는 클라이언트는 "세션" 이라는 단어를 배울 필요가
> 전혀 없고, 연속성이 필요한 클라이언트는 이미 가지고 있는 id 를 그대로 인용함으로써 그것을
> 얻는다.

## 4. 전송

- 모든 요청은 TLS 를 통한 HTTP/1.1 이상이어야 한다(MUST). 단, 루프백 개발 환경에서는 서버가
  평문을 허용해도 된다(MAY).
- 요청과 응답 본문은 `application/json; charset=utf-8` 이다. 단 파일 업로드
  (`multipart/form-data`) 와 파일 다운로드(파일 자신의 미디어 타입)는 예외다.
- 스트리밍은 [Streaming](https://github.com/HarnessRouter/harnessrouter/blob/main/protocol/versions/2026-08-11/streaming.md) 에 기술된 대로 서버 전송 이벤트(`text/event-stream`)를
  사용한다.
- 서버는 `Accept` 헤더가 없는 요청을 받아들여야 하며(MUST) 기본값으로 JSON 을 써야 한다.

## 5. 인증

클라이언트는 베어러 토큰으로 인증한다.

```http
Authorization: Bearer <token>
```

토큰이 어떻게 발급되는지는 범위 밖이다. 서버는 부재하거나 형식이 잘못됐거나 알 수 없는 토큰을
`401` 과 [Errors](https://github.com/HarnessRouter/harnessrouter/blob/main/protocol/versions/2026-08-11/errors.md) 의 오류 모델로 거부해야 하며(MUST), "그런 토큰이 없다" 와
"토큰이 여기서는 허용되지 않는다" 를 호출자가 유효한 토큰을 열거할 수 있는 방식으로 구분해서는
안 된다(MUST NOT).

서버는 모든 객체를 그것을 만든 주체(principal)로 범위를 한정해야 한다(MUST). 클라이언트는 다른
주체의 response, session, file 을 — id 를 추측해서라도 — 읽거나 이어가거나 취소하거나 삭제할 수
없어야 한다(MUST NOT). 서버는 호출자의 범위 밖 객체에 대해 `403` 이 아니라 `404` 를 반환해야
하며(MUST), 그래야 id 의 존재 여부가 노출되지 않는다.

## 6. 설계 원칙

이것들은 명세가 스스로에게 부과하는 규칙이다. 뒤에 나오는 내용의 형태를 설명하기 때문에, 그리고
이것들 중 하나를 어기는 미래의 변경은 아마도 실수일 것이기 때문에 여기 포함된다.

1. 클라이언트는 물어보지 않는 한 어느 하네스가 그 작업을 실행했는지 알 수 없어야 한다.
   클라이언트가 관측할 수 있는 하네스 간의 모든 차이는 누수이며, 각 누수는 하네스를 바꾸는 것이
   제품을 깨뜨리게 되는 지점이다.
2. 진행 상황은 렌더링이 아니라 사실의 스트림이다. 이벤트는 무슨 일이 일어났는지를 기술한다 —
   텍스트, 도구 호출, 파일 — 그것을 어떻게 표시할지는 절대 기술하지 않는다.
3. 필드는 하나만 의미한다. UHP 가 빌려온 표면을 확장할 때는 필드를 추가하지, 재정의하지
   않는다.
4. 부재는 비어있음이 아니고, 비어있음은 0 이 아니다. 어떤 값을 모르는 서버는 그것을
   생략한다. 자리표시자나 추정치나 0 을 지어내서는 안 된다(MUST NOT).
5. 실패는 일급 결과다. 모든 실패는 성공과 같은 봉투 안에서, 기계가 읽을 수 있는 코드와
   함께 보고 가능해야 한다. 클라이언트가 무엇을 해야 할지 알기 위해 산문을 파싱해야 하는 일은
   절대 없어야 한다.
6. 명세와 참조 구현과 적합성 스위트는 함께 움직인다. 어떤 테스트도 강제하지 않는 문장은
   표준이 아니라 소망이다.
