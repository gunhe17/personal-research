# 거버넌스와 변경 절차

UHP는 [HarnessRouter 저장소](https://github.com/HarnessRouter/harnessrouter)에서 메인테이너 주도, 제안 우선 모델로
유지된다. 이 문서는 UHP가 어떻게 변경되는지를 정의한다.

## 원칙

1. **코드보다 산문이 먼저다.** 변경은 풀 리퀘스트가 아니라 문제 설명에서 시작한다. 패치는 답이며, 제안은 먼저 질문을
   세워야 한다.
2. **세 산출물이 함께 움직인다.** 명세서와 참조 구현과 적합성 스위트가 같은 변경 안에서 함께 갱신되지 않으면 어떤
   변경도 반영되지 않는다. 아무것도 강제하지 않는 명세 문장은 소망일 뿐이다.
3. **호환성은 기능이다.** 적합한 클라이언트를 깨뜨리는 변경은 체인지로그의 한 줄이 아니라 새 버전과 마이그레이션
   경로를 요구한다.
4. **기준은 동작하는 구현이다.** 제안은 우아함으로 채택되지 않는다. 무언가가 그것을 실행해야 한다.

## 절차

### 1. 제안

`uep` 라벨이 붙은 GitHub 이슈로 **UHP 개선 제안(UEP)**을 연다. 다음을 포함한다.

- **문제** — 개발자가 오늘 무엇을 구체적으로 할 수 없는가.
- **제안** — 논쟁할 수 있을 만큼 충분히 자세한 변경 내용.
- **호환성** — 무엇이 깨지는지, 그리고 현재 버전을 대상으로 작성된 클라이언트가 무엇을 겪게 되는지.
- **대안** — 그 밖에 무엇을 검토했고 왜 그것이 더 나쁜지.

산문이면 충분하다. UEP는 패치를 필요로 하지 않으며, 패치가 위 항목들을 대신할 수도 없다.

### 2. 논의

메인테이너는 영업일 10일 이내에 **원칙적 수락**, **보완 필요**, **사유를 명시한 거절** 중 하나로 응답한다. 거절은
그 사유와 함께 기록되어, 같은 제안이 처음부터 다시 논쟁되지 않는다.

### 3. 구현

수락된 UEP는 세 산출물을 모두 담은 하나의 풀 리퀘스트로 구현된다.

- [ ] 명세서 챕터 갱신
- [ ] `schema/` OpenAPI + JSON Schema 갱신
- [ ] 참조 구현 갱신
- [ ] 변경 전에는 실패하고 변경 후에는 통과하는 적합성 테스트 추가
- [ ] `CHANGELOG.md` 항목

이들 중 하나라도 빠진 풀 리퀘스트는, 코드가 아무리 훌륭해도 준비된 것이 아니다.

### 4. 릴리스

추가적인 변경은 현재 버전에 실린다. 깨지는 변경은 [VERSIONING.md](https://github.com/HarnessRouter/harnessrouter/blob/main/protocol/VERSIONING.md)에 따라
날짜가 붙은 새 버전으로 누적되며, 마이그레이션 노트와 함께 발행된다.

## 역할

- **메인테이너** — 병합 권한을 가지며, 세 산출물 사이의 일관성과 UEP 응답에 책임을 진다.
- **기여자** — UEP나 풀 리퀘스트나 이슈를 여는 누구든.
- **구현자** — UHP 서버나 클라이언트를 배포하는 누구든. 구현자의 피드백은 모든 설계 논쟁에서 이론적 우아함보다
  우선한다.

## 문제 보고

- **명세서 버그** — 모호함, 구현 불가능한 규칙, 명세와 스위트 사이의 불일치: `spec-bug` 라벨이 붙은 이슈를 연다.
  이들은 결함으로 취급된다.
- **참조 구현의 버그** — GitHub 이슈.
- **보안 취약점** — 공개 이슈가 아니라 비공개 제보로. 저장소의 보안 정책을 참고한다.

## 적합성 주장

"UHP 2026-08-11 conformant (class)"라는 표현은 해당 클래스에서 적합성 스위트를 통과했다는 뜻이다. 그 주장과 함께
보고서를 공개하는 것이 기대된다. 별도의 인증 기관도 없고, 수수료도 없고, 로고 프로그램도 없다. 스위트가 곧
권위이며 이 저장소 안에 있고, 누구든 누구의 서버를 대상으로든 그것을 실행할 수 있다.

## 명칭과 적합성

이 표준의 정식 명칭은 Unified Harness Protocol(UHP)이다. 사이트는 https://unifiedharnessprotocol.org 다.

Apache-2.0은 코드와 명세서에 대한 권리를 그 조건에 따라 부여한다. 프로토콜 명칭에 대한 권리는 부여하지 않는다.
"Unified Harness Protocol"과 "UHP"는 HarnessRouter의 상표다.

구현체는 [`conformance/`](https://github.com/HarnessRouter/harnessrouter/tree/main/protocol/conformance/)의 적합성
스위트를 통과한 경우에만 자신을 "UHP-compatible"이라고 부르거나 "UHP를 구현한다"고 말할 수 있다. 그 스위트를
통과하는 것이 이 프로젝트에서 적합성의 정의다. 비적합 구현체, 부분 구현체, 수정된 포크는 호환성을 암시하는
방식으로 이 명칭을 사용해서는 안 된다. 어떤 제품이 UHP와 "함께 동작한다"거나 "연결된다"고 사실대로 말하는 것은
문제 없다.

상표 및 호환성 주장에 관한 질문은 contact@harnessrouter.ai로 보낼 수 있다.
