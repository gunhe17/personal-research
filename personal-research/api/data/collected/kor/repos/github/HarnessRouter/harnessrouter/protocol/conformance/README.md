# UHP 적합성 스위트

**이 스위트를 통과하는 것이 "UHP conformant" 가 의미하는 바다.** 엔드포인트를 구현했다는 것도, 자체
평가도, 대부분을 통과했다는 것도 의미하지 않는다. 이 스위트는 이 저장소 안에 있고, HTTP 를 통해 어떤
서버에 대해서도 실행할 수 있으며, 누구든 다른 누구의 구현에 대해 이것을 실행할 수 있다.

## 실행하기

```bash
pip install -e protocol/conformance

uhp-conformance \
  --base-url https://your-uhp-server \
  --api-key "$UHP_API_KEY" \
  --class full \
  --json report.json
```

| 옵션 | 의미 |
|---|---|
| `--base-url` | 서버 루트. 스위트가 `/v1/...` 를 자체적으로 붙인다. |
| `--api-key` | 베어러 토큰, 또는 `UHP_API_KEY` 를 설정한다. |
| `--class` | `core`, `extended` 또는 `full`. 누적된다 — `full` 은 전부 실행한다. |
| `--harness-id` | 목록의 첫 하네스 대신 특정 하네스를 대상으로 태스크를 실행한다. |
| `--model` | 특정 모델로 태스크를 실행한다. |
| `--task-timeout` | 하나의 에이전트 태스크에 허용할 초. 기본값 300. |
| `--only` | 콤마로 구분한 체크 id. 하나의 실패를 반복 작업할 때 쓴다. |
| `--json` | 기계가 읽을 수 있는 보고서를 작성한다. |
| `--plain` | ANSI 색상 없음. CI 로그용. |

아무것도 실패하지 않으면 종료 코드는 `0` 이고 그 외에는 `1` 이므로, 변경 없이 CI 에 그대로 넣을 수 있다.

이 스위트는 실제 에이전트 태스크를 실행한다. 약 여섯 개를 보내며 실제 모델 토큰과 몇 분의 시간이
든다. 이것은 의도적이다. 잡을 가치가 있는 결함들 — 절대 플러시되지 않는 스트림, 절대 종료되지 않는
취소, 다운로드할 수 없는 아티팩트 — 은 스키마만 검사하는 것으로는 보이지 않기 때문이다.

## 무엇을 검사하나

세 클래스에 걸쳐 52 개의 체크가 있다.

| 클래스 | 체크 수 | 다루는 범위 |
|---|---|---|
| Core | 37 | 디스커버리, 버전 협상, 인증, 오류 봉투, 하네스, 모델, 태스크 실행(스트리밍 여부 모두), 이벤트 스트림, 세션, 취소 |
| Extended | +8 | 세션 목록 조회와 조회, 파일 입력, 아티팩트, 다운로드 헤더, 경로 순회 탐침 |
| Full | +7 | 하네스 생성/수정/삭제, 지원하지 않는 base 의 거부, 스킬 폴더 왕복, MCP 및 비활성화된 도구의 지속성 |

모든 체크는 자신이 강제하는 명세의 절을 명시하므로, 실패는 테스트 이름이 아니라 위반한 문장을 가리킨다.

몇 개는 특별히 언급할 가치가 있다. 스키마 검사가 결코 잡지 못하는 것들을 잡기 때문이다.

- S-04 — `sequence_number` 는 빈틈이 없고 단조 증가한다. 이것이 없으면 클라이언트는 누락된
  이벤트와 서버가 단순히 번호를 건너뛴 경우를 구분할 수 없다.
- S-09 — 스트림은 점진적이어야 한다. 이벤트 도착 시각의 분산을 측정해, 모든 것을 버퍼링했다가
  끝에 한꺼번에 플러시하는 서버를 실패로 잡는다. 이것은 단연 가장 흔한 UHP 배포 오류이며, 보통
  프록시 설정 때문이고, 무언가 측정하지 않으면 느린 에이전트와 구분이 안 된다.
- C-03 — 실행 중인 태스크가 실제로 멈추는지 본다. 긴 작업을 시작하고 취소한 뒤 종료 상태를
  기다린다. `200` 을 반환하고 에이전트를 계속 돌리는 취소 엔드포인트는 다른 모든 종류의 테스트를
  통과한다.
- X-07 — 아티팩트가 `X-Content-Type-Options: nosniff` 와 함께 다운로드되는지 본다. 아티팩트는
  공격자가 영향을 줄 수 있는 콘텐츠이며, 이 헤더 없이 제공되면 아티팩트는 클라이언트 자신의 출처에
  대한 저장형 XSS 가 된다.
- X-08 — 아티팩트 id 가 자신의 컨테이너 밖으로 순회하지 않는지 본다. `../` 와 그 퍼센트 인코딩
  형태를 탐침한다.
- F-03/F-04 — 스킬은 폴더이며, 무관한 편집을 겪어도 살아남아야 한다. `SKILL.md` 만 저장하거나
  하네스 이름이 바뀔 때 번들을 비워버리는 서버는 다른 모든 체크를 통과한다. 설정은 여전히 올바르게
  보이고, 손실은 나중에 에이전트가 이상하게 행동하는 것으로만 드러난다.

## 결과

| 결과 | 의미 |
|---|---|
| PASS | 요구되는 동작이 관측됐다. |
| FAIL | 동작이 잘못됐음이 관측됐다. 적합성 결함이다. |
| SKIP | 체크를 실행할 수 없었고, 그 이유가 기록됐다. |
| ERROR | 체크 자체가 깨졌다 — 스위트의 버그다. |

**스킵은 절대 통과가 아니다.** 보고서는 스킵을 별도로 명시하고, 그것들이 검증되지 않았다는 것을
반복해서 말한다. 실행하지 않은 체크를 초록색 요약 뒤에 숨기는 스위트는 자신이 세우려는 바로 그것에
대해 거짓말을 시작한 스위트이기 때문이다.

JSON 보고서도 같은 규칙을 스스로에게 적용한다. 이 보고서는 적합성 주장의 증거로 공개되는 산출물이고
그것을 읽는 사람이 실행한 사람이 아닌 경우가 흔하기 때문이다.

- `conformant` 는 모든 체크가 실행됐고 하나도 실패하거나 오류가 나지 않았을 때만 `true` 다. 스킵
  하나만 있어도 `false` 가 된다.
- `conformant_with_skips` 는 실패하거나 오류가 난 것이 없을 때 `true` 다 — 실행된 체크들은
  깨끗하고, 실행되지 않은 것들은 `skipped_not_verified` 에 id 로 나열되므로, 보고서는 자신이
  무엇을 세우지 못했는지를 정확히 말한다.
- `suite_version` 과 `generated_at`(UTC) 은 보고서를 스위트의 리비전과 그것을 만든 순간에 묶는다.
  이 필드들이 없는 보고서는 스위트 `2026.8.11.post1` 이전의 것이다. 이전 실행에서 저장소에 커밋된
  보고서들이 그 옛 형태다.

## 참조 구현 결과

이 저장소의 참조 구현인 HarnessRouter Community Edition 0.3.0 을 2026-08-11 에 실제 인스턴스에
대해 실행한 결과:

```
  Summary
    52/52 passed · 0 failed · 0 skipped · 0 errored
    CONFORMANT — UHP 2026-08-11 (full)
```

이 스위트는 그 구현을 기준으로 개발됐으며, 바로 그렇기 때문에 명세는 적합성이 구현이 아니라 스위트로
정의된다고 말한다. 참조 구현이 하는 일 중 스위트가 요구하지 않는 것은 HarnessRouter 의 동작이지 UHP
요구사항이 아니며, 다른 구현은 그것을 자유롭게 다르게 할 수 있다.

스위트를 작성하고 실행하면서 네 가지 실제 결함이 발견됐다. 셋은 참조 구현에, 하나는 스위트 자체에
있었다.

1. 캐퍼빌리티 디스커버리가 전혀 없었다 — 클라이언트는 추측하거나 `404` 로부터 배워야 했다.
2. 프로토콜 버전이 와이어에 실려 있지 않았다.
3. 실패가 그냥 사람이 읽는 문자열만 반환해서, 클라이언트가 재시도 여부를 결정하려면 산문을
   매칭해야 했다.
4. `POST /v1/harnesses` 가 서버가 실행할 수 없는 base 를 받아들여, 실패를 첫 태스크로 미뤘다 —
   클라이언트가 이미 그것을 커밋한 뒤였다. 첫 번째 전체 실행에서 F-02 에 걸렸다.

도구와 스킬 표면을 실제 에이전트에 대해 테스트하면서 세 가지가 더 발견됐고, 그중 어느 것도 설정
수준 체크로는 볼 수 없는 것들이었다.

5. Hermes 는 HTTP MCP 서버를 전혀 쓸 수 없었다. 이미지가 버전 고정 없이 `mcp` SDK 를
   설치했는데, 이것이 Hermes 가 HTTP 전송을 게이팅하는 심볼을 제거한 버전으로 해석됐다. 그 백엔드에
   설정된 모든 원격 MCP 서버가 조용히 버려졌고, 에이전트는 "그 도구에 접근할 수 없습니다"라고
   답했다 — 모델 거부와 구분이 안 됐다. SDK 는 이제 버전 고정됐고 시작 시 검증되며, 이미 깨진
   버전이 있는 볼륨에서는 그 자리에서 복구된다.
6. Hermes 는 `disabledTools` 를 완전히 무시했다. Claude 는 하드 플래그로 그것을 강제하고
   Codex 는 그것을 지시문으로 받는데, Hermes 는 어느 분기도 없었다. 그래서 도구를 비활성화한
   운영자는 강제도 경고도 받지 못했다.
7. MCP URL 정책은 권고 사항일 뿐이었다. 콘솔의 "Test connection" 버튼에서만 실행됐기 때문에,
   콘솔이 거부한 URL 을 이후 턴이 그대로 연결했다. 이제는 설정 시점과 실행 시점 양쪽에 적용되는
   하나의 함수다.
8. Claude 의 하드 차단은 아무 일도 하지 않았고, 제품은 그것이 하드라고 주장했다. 비활성화된
   도구는 권한 프롬프트 시스템에 속하는 `--disallowedTools` 로 전달됐는데, 자율 실행은 그 시스템을
   끄는 `--dangerously-skip-permissions` 를 전달한다. 그 플래그는 받아들여졌지만 무시됐고, 그래서
   `Bash` 를 비활성화한 운영자는 에이전트가 `Bash` 를 실행하는 것을 지켜봐야 했다. 이 제약은 이제
   런타임의 설정 파일에 거부 규칙으로 기록되며, skip-permissions 플래그도 이를 무시하지 못한다.
   실제 에이전트에 대해 양방향으로 증명됐다. 도구가 활성화됐을 때는 명령을 실행했고, 비활성화됐을
   때는 에이전트가 그런 도구가 없다고 보고했고 실행하지 않았다.

### 이 체크들이 세우지 못하는 것

이 스위트는 `disabledTools` 가 지속된다는 것을 검증하지, 강제된다는 것을 검증하지 않는다.
강제는 의도적으로 검사되지 않는데, §4.3 이 지시문 수준의 강제를 허용하기 때문이며, 지시를 따르는
에이전트는 HTTP 를 통해서는 도구를 차단하는 런타임과 구분이 안 되기 때문이다 — 그래서 행위 기반
체크는 모델이 우연히 순응하는 실행이라면 아무것도 안 하는 차단을 가진 서버도 통과시켜 버릴 것이다.
결함 8 은 행위 기반 체크가 대부분의 실행에서 적합하다고 판정했을 무동작 차단이었다. 강제는 도구를
비활성화하고 에이전트가 그것을 절대 호출하지 않는지 확인함으로써 런타임에 대해 검증되며, 이것은
여기가 아니라 각 구현 자신의 테스트 스위트에 속한다.

## 체크 추가하기

체크는 하나의 요구사항을 단언하는 함수다.

```python
@check("T-08", "Tasks reject an empty input", "core", f"{SPEC}/tasks.md#2-input")
def t08(ctx):
    r = ctx.client.post("/v1/responses", body={"input": ""})
    assert r.status == 400, f"empty input returned HTTP {r.status}, expected 400"
```

좋은 체크를 위한 규칙:

- 참조 구현이 하는 일이 아니라 명세가 말하는 것을 단언한다. 명세가 재량을 허용하는 곳에서는
  체크도 그것을 허용해야 한다 — 그렇지 않으면 스위트는 한 구현의 취향을 강제하게 되고, 다른 모든
  구현은 틀려서가 아니라 다르다는 이유로 실패한다.
- 증거와 함께 실패한다. 메시지는 무엇이 기대됐는지, 무엇이 일어났는지, 왜 그것이 문제인지를
  말해야 한다. `assert r.status == 200` 은 유지보수자에게 아무것도 알려주지 않는다.
- 스킵은 크게, 절대 조용히 하지 않는다. 전제조건이 빠졌다면 `raise Skip("reason")` 을 쓴다.
- 정리한다. 하네스를 만드는 체크는 그것을 삭제한다. 실패했을 때도 포함해서.

[GOVERNANCE.md](https://github.com/HarnessRouter/harnessrouter/blob/main/protocol/conformance/../GOVERNANCE.md) 에 따르면, 체크가 강제하기 전까지는 명세 변경이 완료된 것이
아니다 — 아무것도 테스트하지 않는 규칙은 소망일 뿐이다.
