# 버전 관리와 호환성

## 체계

UHP 버전은 날짜다 — `YYYY-MM-DD`, 그 버전이 발행된 날. `2026-08-11`이 현재 버전이다.

시맨틱 버저닝 대신 날짜를 선택한 것은 의도적인 결정이다. SemVer의 약속은 메이저 증가는 "깨질 것을 각오하라"는
뜻이고 마이너 증가는 "안전하다"는 뜻이라는 것인데, 이 약속은 오직 번호를 매기는 사람의 규율만큼만 유효하고
실제로는 이 규율이 흔히 깨진다. 날짜는 지킬 수 없는 어떤 것도 주장하지 않는다. 그 버전이 언제 발행되었는지를
말해 주고, 정렬되며, 구현체의 노후 정도를 한눈에 드러낸다.

## 버전 안에서 바뀔 수 있는 것

발행된 버전은 구조상 불변이다. 한 버전 안에서 서버는 다음을 할 수 있다(MAY).

- 선택적 요청 필드를 추가한다
- 응답 객체에 필드를 추가한다
- 새 이벤트 타입을 추가한다
- 벤더 접두사를 붙인 새 에러 코드를 추가한다
- 제약을 완화한다(이전에 거부했던 입력을 받아들인다)

서버는 한 버전 안에서 다음을 해서는 안 된다(MUST NOT).

- 필드를 제거하거나 이름을 바꾼다
- 필드의 타입이나 의미를 바꾼다
- 필수 요청 필드를 추가한다
- 이벤트 타입이나 에러 코드를 제거한다
- 제약을 강화한다(이전에 받아들였던 입력을 거부한다)

두 번째 목록에 있는 것은 무엇이든 새 버전을 요구한다.

## 클라이언트 규칙

적합한 클라이언트는 다음을 반드시 지켜야 한다(MUST).

1. 알 수 없는 필드를 무시한다. 경고도, 오류도 아니라 무시한다.
2. 알 수 없는 이벤트 타입을 무시한다. 건너뛰고 스트림 읽기를 계속한다.
3. 알 수 없는 출력 항목 타입을 무시한다. 이해할 수 있는 것만 렌더링한다.
4. 알 수 없는 에러 코드를 그 `type`으로 취급한다. `type: "server_error"`를 가진, 인식하지 못하는 `code`도
   여전히 재시도 가능하다.

이 네 규칙을 따르는 클라이언트는 한 버전 안의 모든 추가적인 변경을 넘어 계속 동작한다. 그것이 이 규칙들을
문서로 남기는 이유 전부다.

## 서버 규칙

서버는 다음을 반드시 지켜야 한다(MUST).

1. `UHP-Version` 응답 헤더에 자신이 제공한 버전을 보고한다.
2. 지원하지 않는 요청 버전은 다른 버전을 대신 제공하는 대신 `unsupported_protocol_version`으로 거부한다.
3. 한 번에 최소 하나의 완전한 버전을 지원하며, 새 버전이 발행된 뒤 최소 여섯 달 동안 이전 버전도 지원해야
   한다(SHOULD).

## 지원 중단

필드나 엔드포인트는 다음 절차로 지원 중단된다.

1. 명세서와 OpenAPI 문서에 사유와 대체물을 함께 붙여 지원 중단으로 표시한다.
2. 최소 두 번의 발행 버전 동안 계속 동작하도록 유지한다.
3. 발표 후 두 번째 버전보다 일찍 제거하지 않는다.

동작하는 대체물이 먼저 존재하지 않은 채로 제거되는 것은 없다.

## 현재 버전이 안고 있는 알려진 타협

명세서 스스로의 거친 지점을 숨긴다면 매끄러운 지점에 대해서도 신뢰할 수 없으므로, 여기에 기록해 둔다.

- 혼재된 필드 표기법. 작업 표면은 `snake_case`이고 하네스 객체는 `camelCase`다. 둘 다 이미 출시된
  클라이언트에서 필수적으로 사용되고 있다. 앞으로의 메이저 버전에서는 이를 통일해야 한다.
- 세션 삭제가 `/v1/traces/{id}`에 위치한다. 이 경로는 세션이라는 어휘가 생기기 전부터 있었다. 이것을
  조용히 이름만 바꾸는 것은 미미한 이득을 위해 기존 클라이언트를 깨뜨리는 일이므로, 있는 그대로 명세에
  담았다. 앞으로의 버전에서는 이를 `/v1/sessions/{id}`로 옮기고, 위의 절차를 거쳐 옛 경로를 지원 중단해야
  한다.
